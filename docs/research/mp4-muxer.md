# Мультиплексор mp4 и сквозное копирование аудиодорожки

Исследование по тикету [#3](https://github.com/Spoonin/klex/issues/3). Дата: 2026-08-17.

## Вывод

**Mediabunny** — единственный вменяемый кандидат. Он закрывает и мультиплексирование, и демультиплексирование, и сквозное копирование аудио, причём именно в той форме, которая нужна нашему конвейеру: мы сами кодируем видео и сами подаём готовые пакеты.

## Кандидаты

| Библиотека | Вердикт |
|---|---|
| [**Mediabunny**](https://github.com/Vanilagy/mediabunny) | **Выбран.** MPL-2.0, ноль зависимостей, чистый TypeScript. 6.9k звёзд, 1314 коммитов. Читает и пишет MP4, MOV, WebM, MKV, HLS, WAVE, MP3, Ogg, ADTS, FLAC, MPEG-TS; 25+ кодеков. Заявлен как tree-shakable «от 5 кБ gzipped», запись `.mp4` — 17.3 кБ. |
| [**mp4-muxer**](https://github.com/Vanilagy/mp4-muxer) | **Отклонён — объявлен устаревшим самим автором.** [Руководство по миграции](https://vanilagy.github.io/mp4-muxer/MIGRATION-GUIDE.html) прямо говорит: «you should always prefer Mediabunny over mp4-muxer — this library is now obsolete». Мультиплексор Mediabunny вырос из него же. |
| **mp4box.js** | **Отклонён.** Работает, но 37.3 кБ против 17.3 кБ, API старше и ниже уровнем, и он не даёт готовой интеграции с WebCodecs. |
| **webm-muxer** | Не рассматривался: нужен `.mp4`, тот же автор, та же судьба, что у `mp4-muxer`. |

Отдельный аргумент в пользу Mediabunny: Remotion принял его и спонсирует, свернув собственные `@remotion/media-parser` и `@remotion/webcodecs`.

## Как это ложится на наш конвейер

Готовый Conversion API нам **не подходит** — он предполагает, что библиотека сама читает вход и пишет выход. У нас между ними стоит композитинг: кадры проходят через WebGL2 и кодируются нашим собственным `VideoEncoder`.

Нужная связка — ручная, из низкоуровневых примитивов:

- **Видео:** `EncodedVideoPacketSource`, в который мы подаём собственные чанки: `EncodedPacket.fromEncodedChunk(chunk)`. Пакеты добавляются в порядке декодирования, метка времени — презентационная, B-кадры библиотека раскладывает сама.
- **Аудио:** `EncodedPacketSink` на входной дорожке — он извлекает **закодированные** пакеты без декодирования — и `EncodedAudioPacketSource` на выходной. Пакеты переливаются из первого во второй; `AudioEncoder`/`AudioDecoder` не задействованы вовсе, а значит дыра в Safari 16.4–18.7 обойдена.
- **Выход:** `StreamTarget`, отдающий данные небольшими порциями через Streams API, вместо `BufferTarget`, который собирает весь файл в один `ArrayBuffer` в памяти.

Схематично:

```ts
const videoSource = new EncodedVideoPacketSource('avc');
const audioSource = new EncodedAudioPacketSource('aac');
output.addVideoTrack(videoSource, { frameRate });
output.addAudioTrack(audioSource);
await output.start();

// видео — свои чанки из VideoEncoder
await videoSource.add(EncodedPacket.fromEncodedChunk(chunk), meta);

// аудио — сквозное копирование, без декодирования
for await (const packet of audioSink.packets()) {
  await audioSource.add(packet);
}
```

`add()` возвращает промис, разрешающийся, когда выход готов принимать дальше — его нужно ожидать, иначе теряется backpressure. Это и есть штатный механизм, удерживающий память в границах.

## Потоковость и память

- Чтение ленивое и по требованию: `packets()` читает только нужные участки файла и предзагружает ближайшие пакеты. Весь файл в память не поднимается.
- Запись потоковая через `StreamTarget`.
- Конвейер библиотеки описан как pipelined с обработкой backpressure.

Это ровно то, что требуется при [бюджете страницы 300–450 МБ в мобильном Safari](https://lapcatsoftware.com/articles/2026/1/7.html).

## Тайминги

Метка времени пакета — презентационная; порядок добавления — декодный. Явной автоматической синхронизации дорожек между собой документация не описывает. Для составных конверсий предлагается пошаговое `execute({ until: timestamp })`, чтобы дорожки продвигались примерно с одной скоростью и не раздували буферы. В нашем ручном варианте ответственность за то, чтобы аудио не убегало вперёд видео на длинном клипе, лежит на нас — **это риск, который должен проверить [измерительный конвейер](https://github.com/Spoonin/klex/issues/7)**.

## Краевые случаи

- **Звука нет.** Аудиодорожку просто не добавляем. В Conversion API аналог — `audio: { discard: true }`.
- **Несколько аудиодорожек.** Есть `tracks: 'primary'` против `tracks: 'all'`; в ручном режиме мы сами выбираем первичную. Для первой редакции разумно брать первую и игнорировать остальные.
- **Кодек не AAC.** Сквозное копирование возможно, только если кодек поддерживается контейнером-приёмником. AAC-LC копируется напрямую. Для прочего (например, звук в MOV с телефона в ином кодеке) сквозной путь недоступен, а перекодировать нельзя — `AudioEncoder` отсутствует на части iOS. **Поведение в этом случае не решено** и вынесено ниже.
- Свойство `discardedTracks` сообщает, какие дорожки исключены и почему — полезно для внятного сообщения пользователю.

## Что осталось нерешённым

Один вопрос, который это исследование вскрыло и который не является research: **что делать, когда аудиодорожка не поддаётся сквозному копированию** — экспортировать без звука, отказать на входе, или перекодировать там, где `AudioEncoder` доступен, и отказывать в остальных случаях. Это решение, а не факт; уходит в туман карты.
